# Nook 私人版独立化设计

## 目标

以 Noty `v1.9.2` 为固定基线，建立仅供个人使用的 macOS 应用 **Nook**。第一阶段只完成产品身份、数据空间与更新渠道的独立化，不改变笔记核心功能和交互，确保后续可以通过 Vibe Coding 安全、持续地迭代。

## 已确认约束

- 仅供个人使用，不公开分发、不商用。
- 基线固定为 Git 标签 `v1.9.2`（提交 `4fc0fed`）。
- 保留原项目 MIT `LICENSE` 和 `licenses/THIRD-PARTY.txt`。
- 目标系统沿用原项目要求：macOS 15 及以上。
- 第一阶段不迁移现有 Noty 数据，Nook 使用全新的独立数据空间。

## 产品身份

- 应用名称：`Nook`
- 可执行文件及应用包：`Nook` / `Nook.app`
- Bundle ID：`local.nook.Nook`
- URL Scheme：`nook://`
- 本地数据目录：`~/Library/Application Support/Nook/`
- 图标：第一阶段保留现有图标结构，但替换为明确区别于 Noty 的 Nook 图标；视觉方向为极简、安静、私人角落。

Bundle ID 使用个人命名空间，使 Nook 与 Noty 能同时安装和运行；数据目录与 URL Scheme 同步独立，避免笔记、偏好设置和自动化入口发生冲突。

## 自动更新策略

第一阶段移除 Sparkle 自动更新能力及其菜单入口，不连接原项目的 appcast。原因是私人改版不能接受 Noty 官方二进制更新，否则可能覆盖 Nook 的定制代码。

保留 Sparkle 的第三方许可文件，记录项目来源和既有依赖历史。未来若需要私人自动更新，再单独设计自己的签名密钥、发布仓库和更新源。

## 代码改动边界

本阶段只修改以下内容：

1. `Info.plist` 中的应用名、Bundle ID、可执行文件名和 URL Scheme。
2. 构建脚本中的应用包名、二进制名、进程名及相关路径。
3. 源码中的数据目录名、URL Scheme、用户可见的 Noty 品牌文案。
4. 移除或禁用 Sparkle 更新器及对应设置入口。
5. 替换应用图标和必要的品牌资源。
6. README 增加 Nook 私人版说明、上游来源和本地构建方法。

不修改笔记模型、SQLite 表结构、加密方式、编辑器、边缘卡片交互、快捷键或导入导出格式。

## 数据与运行流程

Nook 启动后读取独立的用户偏好，并在 `Application Support/Nook` 下创建数据库及资源目录。笔记继续沿用原项目的 SQLite 存储与 AES-GCM 正文加密机制。`nook://` 请求只交给 Nook 处理，不与已安装的 Noty 争抢协议。

由于不迁移旧数据，首次启动状态应为空。若未来需要导入 Noty 内容，优先使用原项目已有的导出/导入功能，而不是直接复制数据库，以降低密钥或结构不兼容风险。

## 异常处理

- 数据目录创建失败时，沿用现有错误处理并输出可定位的本地错误信息。
- URL Scheme 无效或参数缺失时，保持现有安全策略：内容只能成为笔记文本，不执行输入内容。
- 如果源码仍残留原更新地址，构建检查必须失败，避免误发布可被官方更新覆盖的版本。
- Nook 与 Noty 同时运行时，二者必须拥有独立进程名、Bundle ID、偏好和数据目录。

## 验证标准

1. 从 `v1.9.2` 基线能够成功构建 `Nook.app`。
2. macOS 将其识别为独立应用，可与 Noty 同时安装、同时运行。
3. 新建笔记只写入 `Application Support/Nook`，不读取或修改 Noty 数据。
4. `nook://new?text=...` 能创建笔记，`noty://` 不由 Nook 响应。
5. 应用内不再出现 Noty 品牌文案或官方更新入口。
6. 代码和打包产物中不包含原项目 appcast 地址及公钥。
7. 原项目已有测试全部通过，并补充身份隔离和残留字符串检查。
8. `LICENSE` 与第三方许可文件完整保留。

## 后续迭代原则

第一阶段验收后，再逐个设计和实现私人功能。每次迭代只解决一个明确使用场景，并保留 `upstream` 远程仓库，以便评估和选择性吸收 Noty 后续修复；不自动合并上游版本，避免破坏私人定制。
